# Releases

Zop versions are earned milestones. A version denotes a demonstrated language
and toolchain capability, not elapsed time or aspiration. The
[roadmap](roadmap.md) is the canonical contract; GitHub milestones and release
gate issues mirror it in the public
[Zop language roadmap](https://github.com/orgs/zop-lang/projects/1) for
execution.

Pre-milestone bootstrap manifests may use a `0.0.x` development version. That
metadata identifies builds but does not create a tag, GitHub Release, or earned
capability milestone. A public release still requires an exact matching gate.

## Gate model

Every version has one GitHub milestone named exactly `MAJOR.MINOR.PATCH` and one
issue named exactly `Release gate: MAJOR.MINOR.PATCH`. The issue repeats every
roadmap exit criterion as a checkbox and adds release evidence. Other work that
can block the version belongs to the same milestone.

A release is eligible only when:

- every gate checkbox is checked;
- the release-gate issue and every other issue or pull request in the milestone
  are closed;
- the milestone itself is closed;
- `Cargo.toml`, `Cargo.lock`, the changelog, documentation, and tag agree on the
  version;
- the full compiler, conformance, documentation, packaging, and installation
  checks pass from the tagged commit; and
- the published artifacts and attestations match the successful workflow.

Closing an issue is not evidence by itself. Each checkbox links to tests,
measurements, artifacts, or a merged contract. If the roadmap changes, update
its mirrored gate issue in the same pull request. A missing primary target or
failed target never degrades to another backend.

The gate issue encloses its exact roadmap text between
`roadmap-section:start` and `roadmap-section:end` markers. Publication
normalizes completed checkboxes and compares that block byte-for-byte with the
tagged roadmap section, so documentation and project state cannot drift.

The release workflow independently rejects a publication when the matching
milestone is absent, duplicated, open, or contains open work; when its one
release-gate issue is absent, duplicated, open, or contains unchecked boxes; or
when the tag is not `vMAJOR.MINOR.PATCH` with an optional prerelease suffix.

## Publication

Releases are dispatched manually from the generated `Release` workflow. Tag
pushes do not publish. The operator enters the intended `vMAJOR.MINOR.PATCH`
tag only after the gate closes. `dry-run` exercises planning and artifact builds
without creating a release.

The workflow is generated by cargo-dist 0.32.0 from `dist-workspace.toml`.
cargo-dist builds the archives and shell installer, generates SHA-256 checksums,
attests the artifacts, creates the GitHub release and tag, and uploads the
source tarball. Hand edits to the generated workflow are overwritten; custom
policy lives in reusable workflows and `release/` setup steps.

After publication, install the archive and shell installer into empty prefixes,
run `zop --help`, compile the release smoke corpus, and compare the recorded
checksums and attestations. A failed post-publication check leaves the release
failed and visible for audit; it is not silently replaced in place.

## Bootstrap support matrix

The 0.1.0 binary release supports `aarch64-apple-darwin` and requires Homebrew
LLVM 22 at build and run time. This is deliberately narrower than the language's
target ambitions. The 0.5.0 target-breadth milestone must replace this bootstrap
constraint with a declared, conformance-tested native matrix before claiming
portable releases.

Install the bootstrap prerequisite before the cargo-dist shell installer:

```sh
brew install llvm
curl --proto '=https' --tlsv1.2 -LsSf \
    https://github.com/zop-lang/zop/releases/latest/download/zop-installer.sh \
    | sh
```

## Release changes

Each user-visible pull request includes a changelog line or explains why the
change is internal. Before publication, move accumulated entries from
`Unreleased` under the exact version and date. Release notes link the milestone,
gate issue, compatibility boundary, support matrix, known limitations, and
published conformance evidence.
